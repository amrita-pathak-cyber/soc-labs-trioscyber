# Day 14: Web/HTTP Log Inspection

## Task
Generate requests to a local test web service, identify the client IP, request method, URL path, status code and user-agent for each request, and use `grep` to flag unusual status codes and repeated requests in the log.

**Tools:** Kali Linux, a small Python web server, Firefox, `curl`, `grep`

> **Data note:** The web server script (`web_server.py`) is adapted from Python's standard `http.server` library and not written from scratch. Python's default server doesn't log the User-Agent field, so a short custom handler was needed to capture all five fields. All traffic was generated by me on my own lab VM. The "scanner" requests, the faked sqlmap user-agent and the repeated burst are simulated patterns and were not aimed at any outside system.

## What I did
- Ran the logging server on port 8080, writing the client IP, method, path, status code and user-agent of every request to `access.log`
- Browsed to the server in Firefox over the loopback address to produce normal traffic
- Used `curl` against the VM's real address (192.168.84.128) to produce scan-style traffic: three probes for paths that don't exist (`/admin`, `/wp-login.php`, `/.env`) and one request to a real path with a faked `sqlmap/1.6` user-agent
- Sent a burst of five identical requests to `/about` with a shell loop
- Caught what looked like a missing user-agent field. Checking one log line on its own with `tail` showed the field was there and two narrow terminal windows had cut off the long lines
- Read the full 13-line log, then filtered it with three `grep` commands for status codes, the faked user-agent and the repeated requests

## Results
| Item | Result |
|---|---|
| Requests logged | 13 |
| Distinct client IPs | 2 (127.0.0.1 for Firefox, 192.168.84.128 for `curl`) |
| 4xx and 5xx responses | 4, all 404s |
| Suspicious user-agent | 1 request faking `sqlmap/1.6` |
| Repeated requests (same IP, same path) | 6 to `/about` from 192.168.84.128 |

## Key findings
- Three 404s for `/admin`, `/wp-login.php` and `/.env` from one source in quick succession form a believable reconnaissance pattern. A single 404 would prove very little
- The fourth 404, `/favicon.ico`, was just Firefox asking for a tab icon, so not every 404 is suspicious
- The faked sqlmap request hit a page that exists and got a 200. That is a different signal from a probe against a missing page, and it is visible only by reading the user-agent field
- The "missing" user-agent was a display problem, caught before it could be reported as a real finding

## Key takeaway
Reconnaissance shows up in web logs before anything is compromised, as a cluster of 404s on paths scanners favor. Status codes give a fast first sort, but each flagged line still has to be read. A 404 can be a probe or a browser fetching an icon, and a faked user-agent on a valid path tells a different story from a probe on a missing one. Check one line on its own before calling an odd-looking log a finding.
